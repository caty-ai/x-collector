# X Collector V2 — 設計ドキュメント

> **最終更新**: 2026-03-06

## 概要

V1で構築した7プラットフォーム自動収集基盤の上に、「精査→製本」パイプラインを構築する。
収集した情報からノイズを除去し、カテゴリ分類・一面選定を経て、日刊AI新聞として製本する。

---

## 全体アーキテクチャ

```
記事取得（DB — V1基盤）
  ↓
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【Step 0】前処理・正規化
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  → 媒体差を吸収する正規化レイヤ
  → title / body / url / platform / publishedAt / sourceUrl を統一
  → 短文媒体（X/FB/IG）はURL先タイトル自動補完
  → raw_ingest（原本保持）+ pipeline_items（正規化済み）の2層構成
  ↓
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【Step 1-3】軽量LLM × 1記事ずつ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ① ノイズ判定（共通基準 + 媒体別基準）
  ② Primary タグ付与（1つ）
  ③ Sub タグ付与（該当する場合）
  ④ Action タグ付与（APPLY / EVAL / WATCH / INFO）
  → NOISE → DBにフラグ、以降スキップ
  → PASS  → 次のステップへ
  ↓
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【Step 4】高性能LLM × 全記事横断
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ① DUP検出（同一トピック → 最詳版を残す）
  ② HEADLINE_CANDIDATE 判定（全体俯瞰で一面記事選定）
  ③ PUBLISHED照合（過去の製本済み記事と重複チェック）
  ④ VoiceSignal抽出（小粒投稿のセンチメント集約）
  ↓
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【Step 5】製本（高性能LLM / Opus級）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  → テンプレートに沿ってセクション配置
  → キャッチーな要約タイトル生成
  → 引用元URL付与（原文 + x-collector投稿URL）
  → 「市場の声・実ユーザー評価」セクション（VoiceSignal集計）
  → Markdown出力
  → 「YYYY年MM月DD日 AI Daily News」として保存
```

### LLM 3層構成

| ステップ | モデルクラス | 用途 |
|---------|------------|------|
| Step 0 | なし（ルールベース） | 正規化・前処理 |
| Step 1-3 | 軽量LLM（無料/低コスト） | 1記事単位のノイズ判定＋タグ付与 |
| Step 4 | 高性能LLM | 全記事横断のDUP・HEADLINE・PUBLISHED・VoiceSignal判定 |
| Step 5 | 高性能LLM（Opus 4.6級） | 最終製本・要約タイトル生成 |

## タグ体系

### Primary Tag（Step 1-3で付与、必ず1つ）

| タグ | 製本セクション | 説明 |
|------|--------------|------|
| `UPDATE` | アップデート情報 | モデル・ツール・OSSの更新 |
| `AGENT` | エージェント | エージェント製品・構築・運用・オーケストレーション |
| `TECH` | 技術速報 | 実装手法・プロンプト・コンテキスト・RAG/検索 |
| `RESEARCH` | リサーチ・論文 | 論文・ベンチマーク・評価 |
| `MCP_API` | MCPサーバー・API情報 | MCP / API新着 |
| `DEVICE` | AIデバイス情報 | ハードウェア・ウェアラブル |
| `SECURITY` | セキュリティリスク | 事件・脆弱性・注意 |
| `REGULATION` | 規制・政策・ガバナンス | 法律・ガバナンス |
| `BUSINESS` | ビジネス・資金調達 | 調達・M&A・提携 |
| `COLUMN` | AIおもしろコラム | ユーモア・カルチャー |
| `OTHER` | その他注目の内容 | 分類外の価値ある情報（最後の手段） |

### Sub Tag（Step 1-3で付与、該当する場合のみ）

| タグ | 親 | 製本サブセクション |
|------|-----|-----------------|
| `NEW_LLM` | UPDATE | 新着LLM |
| `LLM_UPDATE` | UPDATE | 既存LLM・CLI・IDE新機能 |
| `OSS_FW` | UPDATE | OSS・フレームワーク |
| `AGENT_DEV` | AGENT | エージェント開発・SDK |
| `AGENT_OPS` | AGENT | エージェント運用・評価 |
| `MULTI_AGENT` | AGENT | マルチエージェント・A2A |
| `PROMPT` | TECH | 話題のプロンプト |
| `CTX_ENG` | TECH | コンテキストエンジニアリング |
| `RAG_SEARCH` | TECH | RAG・検索・埋め込み |
| `PAPER` | RESEARCH | 注目論文・手法 |
| `BENCH` | RESEARCH | ベンチマーク・評価 |
| `MCP` | MCP_API | MCPサーバー・クライアント |
| `SDK_API` | MCP_API | API・SDK・連携基盤 |
| `WEARABLE` | DEVICE | ウェアラブル |
| `ROBOTICS_HW` | DEVICE | ロボティクス・ハードウェア |

### Action Tag（Step 1-3で付与、必ず1つ — 2軸目）

| タグ | 意味 | 用途 |
|------|------|------|
| `APPLY` | すぐ試す価値あり | 実装タスク化候補 |
| `EVAL` | 比較検証が必要 | A/B、他モデル比較 |
| `WATCH` | 継続観測 | 急がないけど追う |
| `INFO` | 共有のみ | 参考情報 |

> **2軸タグ設計**: カテゴリ（primary/sub）× アクション（action）で、
> 「何の話か」と「次に何するか」を同時に分類する。

### 補助タグ（Step 4で付与）

| タグ | 用途 |
|------|------|
| `HEADLINE_CANDIDATE` | 一面掲載（Step 4で横断判定） |
| `DUP` | 重複記事（最詳版以外に付与） |
| `PUBLISHED` | 製本済み（二重掲載防止） |

> **注**: `HEADLINE` は独立カテゴリではなく「昇格枠」。
> 記事は本来のPrimaryカテゴリに属しつつ、一面にも掲載される。

### VoiceSignal（センチメント集約）

小粒の投稿（短いツイート等）をノイズとして捨てず、「声」として集約する仕組み。

- **topic**: 何についての声か（例: "GPT-5.4 High", "Claude Opus 4.6"）
- **sentiment**: positive / negative / neutral
- **usageContext**: 用途文脈（coding, ideation, speed, cost 等）
- 日次集計して製本の「市場の声・実ユーザー評価」セクションに反映

> 通知・音声配信機能（breaking news等）は別モデル（将来の `NotificationQueue`）で対応。

## ノイズ判定基準

### 全媒体共通基準（4項目）

以下のいずれかに該当すれば NOISE:

1. **実質的な情報がない** — 感想のみ、絵文字だけ、リアクション的な短文
2. **AI・テクノロジーと無関係** — 対象ドメインに該当しない内容
3. **情報の実体がない転載** — 原文リンクもなく、スクリーンショットだけで独自情報ゼロ
4. **古い情報の再浮上** — 1ヶ月以上前の既知情報を新情報として再投稿

> **方針**: 宣伝・アフィリエイト目的でも情報の質が良ければ掲載する。
> 情報の質で判断し、宣伝かどうかは除外基準にしない。

### 媒体別追加基準

共通4項目をベースに、媒体ごとの特性に合わせた判定基準を個別に設計する。

| 媒体 | 追加基準 | ステータス |
|------|---------|----------|
| X (Twitter) | 🔲 未策定 | 個別設計が必要 |
| Instagram | 🔲 未策定 | 個別設計が必要 |
| Facebook | 🔲 未策定 | 個別設計が必要 |
| Reddit | 🔲 未策定 | 個別設計が必要 |
| Qiita | 🔲 未策定 | 個別設計が必要 |
| GitHub | 🔲 未策定 | 個別設計が必要 |
| RSS/YouTube | 🔲 未策定 | 個別設計が必要 |

## LLM キャラクター設定（Step 1-3 共通プロンプト）

> 以下の `AI Daily News` は、この設計文書で使う既定の題字です。Step 1-3 の実行時プロンプトでは、`docs/prompts/step1-3/` の `{{NEWSPAPER_MASTHEAD}}` を読み込み時に `getMasthead()` の値へ置換します。運用上の注意は [operations.md](operations.md#紙面題字と-step1-3-実行時プロンプト) を参照してください。

```
あなたはAI Daily Newsの腕きき記者です。
AIに関する情報をあらゆる角度から見極めてピックアップする、
プロ中のプロです。

今回、あなたの元に下記の内容が送られてきました。
あなたが執筆する新聞の内容として今回の内容が適切か？
面白いポイントや読者が知るべき内容か？検討してください。
その上で下記のルールに従って振り分けをしてください。
```

> キャラクター設定の詳細（トーン・専門性・判断軸）は別途策定予定。

### 各記事の書式

```
要約タイトルをキャッチーな内容で
要約テキスト
要約テキスト
要約テキスト
引用元：URL(原文) / URL(x-collectorの対象の投稿URL)
```

### 重複排除・既読管理

- 既に製本済みの情報は二重掲載しない（`PUBLISHED` タグで管理）
- 複数ソースから同一情報が出た場合 → 最も詳しい記事を採用、他は `DUP` フラグでスキップ（削除はしない）

## 実行環境（検討中）

AI精査フェーズの実行方式:

| 方式 | 説明 | メリット | デメリット |
|------|------|---------|----------|
| **案A: オンライン完結** | Railway等でOpenRouter APIキーを使い自動処理 | PC負荷なし、24h稼働 | APIキー管理の検討が必要 |
| **案B: ローカル処理** | MBP/Mac miniがオンライン時のみサブエージェント処理 | APIキー管理が容易 | PC負荷、稼働時間制限 |

> 採用方針: できればオンライン完結（案A）
> APIキーのDB保持方法は要相談
