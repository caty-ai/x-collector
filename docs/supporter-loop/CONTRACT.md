## 0. Design invariants [frozen]

1. **Thanks, not solicitation.** Every message and artifact is a thank-you for something already done. Nothing asks for a Star, a share, or a follow. Copy that violates this is a contract violation, not a style issue.
2. **GitHub-native delivery only.** The only outbound channels are (a) a repository collaborator invitation to the reward repo and (b) a comment on the actor's own Issue / PR in the source repo. No e-mail, no DM, no third-party API is ever called with the actor as recipient. (Telegram is an *owner-side* notification, §9, never a supporter-facing channel.)
3. **Record-only first.** The central workflow ships and runs in `mode: record-only` (§5). Switching to `live` is human checkpoint #4 of EPIC #119 and requires an owner approval comment; the switch is a one-word change in the caller (§4.3) and nothing else.
4. **Least privilege, two single-purpose credentials.** Exactly two long-lived credentials exist (§8), both scoped to the reward repo only and never used against the source repo — the sole exception being the read-shaped §8.4 over-scope probes, which MUST fail: `SUPPORTER_LEDGER_TOKEN` (Contents only — ledger and `SUPPORTERS.md`) and `SUPPORTER_LOOP_TOKEN` (Administration — invitations and revokes). The Administration-capable token is loaded **only** by the `act` job, which does not run in `record-only` (§4.4). Supporter-facing comments use the caller's `GITHUB_TOKEN`. The sweep's stargazer listing (§11 precondition (b)) is the one read the platform refuses to every credential above except a `GITHUB_TOKEN` carrying `contents: write` (v1.11, measured — §11(b)); it therefore runs in a dedicated `stars` job (§4.4) that holds that permission and nothing else — no PAT, no Telegram secret, no checkout, one `GET` — and exists only in sweep runs.
5. **Ledger is the source of truth.** Every decision — including "did nothing" — is one NDJSON line (§6). `SUPPORTERS.md` and every report are derived from the ledger, never the other way round. **Derived files (v2.0, explicit):** the ledger remains the source of truth for every *supporter-facing* decision (delivery, skip, revoke, quota stop — all of them lines). Two files in the reward repo are *derived* and never decisions: `SUPPORTERS.md` is a **pure projection** of the ledger (§6.5); `ledger/<name>.sweep-state.json` (§6.6) is an **owner-notification latch** that also carries Actions-API facts (cancelled runs) and capacity figures. Nothing supporter-facing depends on either; if one is lost or corrupt, the next live sweep regenerates it and the only side effect is at most one duplicate owner Telegram (self-healing). Neither file may be read back to make a supporter-facing decision.
6. **Idempotent by construction.** A supporter receives each reward at most once per generation (§7). Re-delivered webhooks, re-runs, and duplicate events are safe.
7. **Family and bots are excluded.** Accounts in the family roster (§3.2) and bot accounts never receive rewards and never appear in `SUPPORTERS.md`.

## 2. Tier definitions [frozen]

Tiers are **cumulative** in *entitlement*: reaching tier N grants everything from tiers 1..N. Delivery is per tier and idempotent (§7); reaching tier 3 directly (first contact is a merged PR) delivers tiers 1, 2 and 3 in one run.

| Tier | Trigger event (source repo) | Qualifying condition | Delivered | Decided in v1 |
|---|---|---|---|---|
| **1** | `watch` (`action: started`) | Actor not excluded (§3) | **Invitation to the reward repo** (collaborator with permission **`pull`** — the REST enum value; `act` MUST send `{"permission":"pull"}` on every `PUT`, because the platform default when the field is omitted is `push`) + **`SUPPORTERS.md` entry** (login + tier + date) + the **Supporter badge** (an image in the reward repo the supporter may embed; delivered implicitly by repo access) | yes |
| **2** | `issues` (`action: opened`) or `discussion` (`action: created`) | Actor not excluded (v1 has **no spam check**: a spam Issue earns tier 2 like any other; spam handling is an explicit non-goal of the sweep, §11, and is the owner's manual job — block the user, which also makes future invitations fail) | Tier 1 + **one thank-you comment** on that Issue / Discussion (§10) + `SUPPORTERS.md` tier updated to 2 | yes |
| **3** | `pull_request_target` (`action: closed`, `merged == true`) | Actor = PR author, not excluded | Tier 1 + 2 (comment goes on the merged PR) + `SUPPORTERS.md` tier updated to 3 + listing in the source repo's **Contributors wall** and **release notes** (both produced by child #3's `release.yml` from git history, not by the central workflow) | yes |
| Fork | `fork` | — | **Nothing.** Not even a ledger line (the caller does not subscribe to `fork`). | yes (no reward) |

**The tier-1 bundle is atomic under deferral (v2.0).** Invitation, `SUPPORTERS.md` entry and badge are one bundle: nothing in it may assert access that does not yet exist. When the platform refuses the invitation for the rolling 24 h invitation limit (§14, `deferred-quota`), the event run sends **none** of the three (nor a tier-2/3 comment) and the tier-1 bundle is delivered later — by the actor's next tier event or by the sweep's catch-up (§11 step 4b); a deferred tier-2/3 **comment** is retried only by the actor's next qualifying tier event once an invitation stands, because catch-up never posts comments — under the platform's 50 invitations per rolling 24 h, of which catch-up uses at most 45 (§16; the 5-invitation margin covers invitations invisible to the sweep's count). The wait is honest because the supporter is shown nothing before access exists.

### 2.1 Items deferred to a later contract version (decided: **後回し / deferred**)

The strategy note (alpha-wiki `supporter-reward-loop-strategy.md` §7) listed "one more repo invitation" for tier 2 and a "contributor repo invitation" for tier 3. v1 **defers both** and delivers tier 2 and 3 as in the table above.

- Why: the owner decided on 2026-09-05 that no new repository is created for this Epic and that the reward repo is `caty-ai/ask-ai-widget` only. A second private repo does not exist, so a second invitation has nothing to point at. Defining it now would freeze an interface to an artifact nobody owns.
- Exit trigger (re-opens this item as a contract bump, not silently): the owner names a second reward repo *or* the first early-access item rotates out (§12) and a second private repo becomes the natural place for the next one. Until then tier 2 and 3 add **recognition** (comment, tier label, wall, release notes), not further access.
- Consequence for §8: both tokens' repository access stays a single repo. If the deferral is lifted, §8 is bumped and human checkpoint #2 (token issuance) is repeated for the new scope.

### 2.2 Downgrade

Tiers never decrease. Unstarring after tier 2 or 3 is reached does not revoke anything. Unstarring at tier 1 is handled by the sweep (§11 step 4; unchanged in v2.0 — owner decision 2026-09-08).

### 3.1 Included

- Any GitHub user account (`type == "User"`) that performs a tier trigger on a source repo listed in the caller.

### 3.2 Excluded (no reward, no `SUPPORTERS.md` entry; ledger line with `action: skip`, `result: excluded-<reason>`)

| Reason code | Rule |
|---|---|

| `excluded-bot` | `type == "Bot"` or login ends with `[bot]`. |
| `excluded-self` | Actor equals the repository owner org's login or the workflow's own identity. |
| `excluded-org` | `type == "Organization"`. |
| `excluded-member` | On events that carry `author_association` (`issues`, `discussion`, `pull_request_target`) the value is `OWNER` or `MEMBER` — the same first-line check `external-input-watch.yml` applies; the roster stays as defense in depth. `watch` carries no association, so for `watch` the roster is the only check (the sweep MAY additionally drop roster members it finds in the ledger). |

- Prior tier already reached → this is a **dedup** (§7), recorded as `action: skip`, `result: already-<tier>`, not as an exclusion.

### 4.2 `on: workflow_call` — inputs

```yaml
on:
  workflow_call:
    inputs:
      mode:
        description: "record-only | live. Anything else fails the run before any step touches the network."
        required: true
        type: string
      reward_repo:
        description: "owner/name of the private reward repo (ledger + invitations)."
        required: false
        type: string
        default: "caty-ai/ask-ai-widget"
      tiers_enabled:
        description: "Comma-separated subset of 1,2,3. Events for a disabled tier are ledgered as action=skip result=tier-disabled."
        required: false
        type: string
        default: "1,2,3"
      sweep:
        description: "true only from the scheduled sweep job (§11). Mutually exclusive with a tier event."
        required: false
        type: boolean
        default: false
    secrets:
      SUPPORTER_LEDGER_TOKEN:
        description: "Fine-grained PAT, reward_repo only, Contents R/W (§8). Used by decide (ledger) and act (SUPPORTERS.md). Required in both modes."
        required: true
      SUPPORTER_LOOP_TOKEN:
        description: "Fine-grained PAT, reward_repo only, Administration R/W (§8). Loaded only by the act job; may be left unset until checkpoint #4. act fails loud if empty in live."
        required: false
      TELEGRAM_BOT_TOKEN:
        description: "Owner notification bot (§9)."
        required: true
      TELEGRAM_CHAT_ID:
        description: "Owner notification chat (§9)."
        required: true
```

Rules:

- The four secrets above are the complete list (naming rule: `UPPER_SNAKE`, each with an explicit `required`, exactly as `external-input-watch.yml` does; `SUPPORTER_LOOP_TOKEN` is the only optional one, §8.1). A caller passing any other secret fails validation; `secrets: inherit` is forbidden (§4.3).

- `mode` MUST be validated as the **first** step. Any value other than the two literals fails the job with `::error::` and exit 1 before any `gh`/`curl` call.
- `inputs.*` are caller-controlled constants, never actor-controlled; they MAY be used in `${{ }}` expressions. Actor-controlled strings (login, title, body) MUST enter `run:` scripts only through `env:` or `$GITHUB_EVENT_PATH`, never inline via `${{ }}` (same invariant as `external-input-watch.yml`).
- The source repo is `github.repository` of the caller; there is no input for it.

### 4.3 Caller — frozen shape

```yaml
name: supporter-loop
on:
  watch:
    types: [started]
  issues:
    types: [opened]
  discussion:
    types: [created]
  pull_request_target:
    types: [closed]
  schedule:
    - cron: "17 3,15 * * *"   # sweep twice daily, 03:17 and 15:17 UTC (v2.0, §11)
  workflow_dispatch:          # sweep on demand (write access to the caller repo required — v2.0 wording); same steps as the schedule, no inputs
permissions:
  contents: write        # ceiling only (v1.11): materialized solely by the sweep-only `stars` job (§4.4); decide/act stay contents: none
  actions: read          # sweep precondition: "no failed supporter-loop runs since last sweep" (§11)
  issues: write
  pull-requests: write
  discussions: write
# Load-bearing: two lanes per source repo (v2.0, §16). Event runs serialize among
# themselves so two deliveries of the same event cannot both miss the comment
# marker (§7). The sweep has its own lane so a burst of Stars can never cancel
# the pending sweep (GitHub keeps one running + one pending run per group and
# cancels the rest). Do not delete, do not merge the lanes.
concurrency:
  group: ${{ (github.event_name == 'schedule' || github.event_name == 'workflow_dispatch') && format('supporter-loop-sweep-{0}', github.repository) || format('supporter-loop-{0}', github.repository) }}
  cancel-in-progress: false
jobs:
  loop:
    uses: caty-ai/.github/.github/workflows/supporter-loop-reusable.yml@main
    with:
      mode: record-only          # <- the ONLY line that changes at checkpoint #4
      sweep: ${{ github.event_name == 'schedule' || github.event_name == 'workflow_dispatch' }}
    secrets:
      SUPPORTER_LEDGER_TOKEN: ${{ secrets.SUPPORTER_LEDGER_TOKEN }}
      SUPPORTER_LOOP_TOKEN: ${{ secrets.SUPPORTER_LOOP_TOKEN }}
      TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
      TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
```

This block is the **single copy** of the caller shape; §4.4 refers to it and does not restate the `concurrency` block. The two concurrency lanes (v2.0) are `supporter-loop-<repo>` for tier events and `supporter-loop-sweep-<repo>` for `schedule` / `workflow_dispatch`; both keep `cancel-in-progress: false`. A sweep may therefore run **in parallel with one event run**; the contract tolerates that race by construction — ledger appends use §6.4 CAS; a same-actor double invitation is caught by the §7 preflight (`already-1`, no `PUT`) or, if both runs passed preflight before either `PUT`, by GitHub's 204 on the existing invitation — that second `PUT` is ledgered like any other `PUT` response (`ok` on the event path, `ok-catchup` on the sweep path) and counts conservatively toward B and the catch-up attempt bound; `already-1` is written only from preflight, never after a `PUT`; a sweep revoke against a stale stargazer list while an event run re-invites is bounded to ≤ 24 h and self-heals at the next sweep (gen + 1, ledgered); catch-up never posts comments, so the marker race stays impossible; and `SUPPORTERS.md` is regenerated in the GET → read → render → PUT order of §6.5 on every live sweep. The caller adopts the lane split (A2) before the twice-daily cron (A3), and the cron only after the central workflow implements §11 step 4b (child B) — the schedule must never claim catch-up before the workflow can do it.

- `secrets: inherit` is **forbidden** in the caller (same rule as `external-input-caller.yml`).
- The caller's `permissions` block is a **ceiling**: a called job can only downscope it, and each job mints its own `GITHUB_TOKEN`. `contents: write` in the ceiling (v1.11) exists for exactly one called job, `stars`, which runs only when `sweep == true` (§4.4); on every supporter-facing event (`watch`, `issues`, `discussion`, `pull_request_target`) that job is skipped and no token with `contents` above `none` is ever minted — this is what keeps `pull_request_target` safe together with the no-checkout rule. `decide` and `act` MUST keep `contents: none`. The caller never checks out code.
- `discussions: write` is present only for the tier-2 thank-you comment on a Discussion (GraphQL `addDiscussionComment`). Repos without Discussions leave the `discussion` trigger as a no-op.
- The `@main` pin follows the org precedent (`external-input-caller.yml`): `caty-ai/.github` `main` is merge-only via reviewed PR.

### 4.4 Central workflow — jobs and permissions [frozen]

The central workflow MUST be split into two delivery jobs (`decide`, `act`) plus a failure-`alert` job and, since v1.11, a sweep-only `stars` job — four in total — so that *record-only cannot send* by construction:

| Job | Runs when | `permissions` | May use |
|---|---|---|---|
| `stars` (v1.11) | `inputs.sweep == true` only (`timeout-minutes: 10` — v2.0, §16 ceiling S ≈ 80,000 time-bound) | `contents: write` and nothing else — the only job in the loop with `contents` above `none`, because `GET /repos/{source_repo}/stargazers` is refused to every other credential (§11(b)) | `GITHUB_TOKEN` for exactly one paginated `GET /repos/{source_repo}/stargazers`; **no** PAT, **no** Telegram secret, no checkout, no other network call. Output: the numeric stargazer ids only, plus an `ok` flag; `decide` consumes them via `needs.stars.outputs` and treats a missing/failed handoff as precondition (b) false. Pinned by child #2's interface test (one step, `--method GET`, no `secrets.` reference) |
| `decide` | always (`needs: stars`, `if: !cancelled()` so a skipped `stars` on non-sweep events does not skip it) | `contents: none`, `actions: read`, `issues: read`, `pull-requests: read`, `discussions: read` | `GITHUB_TOKEN` (read) · `SUPPORTER_LEDGER_TOKEN` (Contents only) in the steps that read/append the ledger (§6) · **never** `SUPPORTER_LOOP_TOKEN` (the secret is not referenced anywhere in this job) · **no** Telegram secrets (§9 is live-only) |
| `act` | `needs: decide` **and** `inputs.mode == 'live'` **and** (`decide` produced at least one live action **or** `inputs.sweep == true`); its first step is the token preflight (§8.1) on which every other step depends; `timeout-minutes: 10` (v2.0 — pinned, because §11 step 4b's wait and pacing budgets are sized against it) | `contents: none`, `issues: write`, `pull-requests: write`, `discussions: write` (no `actions: read` — the step-8 run counts come from `decide`) | `GITHUB_TOKEN` (write, source repo comments) · `SUPPORTER_LOOP_TOKEN` (reward repo invitations / revokes) · `SUPPORTER_LEDGER_TOKEN` (`SUPPORTERS.md` and the ledger lines for the actions it executed) · Telegram secrets (§9) |
| `alert` | `needs: [stars, decide, act]` (v1.11: `stars` named so the message can name it) with `if: ${{ !cancelled() && failure() && inputs.mode == 'live' }}` (a skipped `act` or `stars` does not suppress it; `timeout-minutes: 2`) | none (`permissions: {}`) | Telegram secrets only (§9) — one message naming the failed job and the run URL; no ledger, no PATs |

- **Sweep job assignment (v1.9 clarification; v2.0: step 8).** In `record-only` the whole sweep runs in `decide` (reduced audit §5.3; step 2 is a no-op; nothing destructive). In `live`, `decide` performs only what the ledger token and `GITHUB_TOKEN` can do — §8.4 ledger-token half, ledger read, the stargazer handoff from `stars` (v1.11), preconditions (a)(b), **and the step-8 cancelled-run listing (v2.0: `decide` is the only delivery job holding `actions: read`; it hands the two counts to `act` through job outputs exactly like the stargazer handoff — `act` gains no permission)** — and hands over; **§11 steps 2–8 (step 8 = rendering the state file and sending the summary from the counts `decide` supplied), preconditions (c)(d)(e) — (c) being the loop-token half of §8.4, i.e. the `act` token preflight itself — run in `act` after the token preflight**, because they need `GET /repos/{reward_repo}/invitations` (Administration) and/or write live-vocabulary lines (`cancel-invite`, `revoke`, recovered `comment`), which the authorship table reserves for `act`. Nothing in this paragraph lets `decide` hold the Administration token.
- The Administration-capable credential (`SUPPORTER_LOOP_TOKEN`) is referenced **only** inside `act`. A job-level `permissions` map restricts `GITHUB_TOKEN`, not a PAT — which is exactly why the PAT that can invite is kept out of the job that runs in `record-only`. Child #2's static check (below) MUST also fail if the string `SUPPORTER_LOOP_TOKEN` appears anywhere in the `decide` job.

**Who writes which ledger line** (§6):

| Line | Written by | When |
|---|---|---|
| every `would-*` line (record-only) — including the record-only catch-up rehearsal's `would-invite` / `would-supporters-append` (§11 step 4b) | `decide` | after the decision, before the job ends |
| every `skip` line written on the event path and in `record-only` (both key namespaces) | `decide` | same |
| the live sweep's catch-up `skip` lines (v2.0): `excluded-<reason>` for a candidate the §3 filter rejects after the identity call, `excluded-unresponsive` after the §7 two-invitation bound, and the single `deferred-quota` stop line (§14) — all `<repo>:sweep:<actor_id>` | `act` | at the point the decision is made (ledger-only) — these decisions are only reachable inside `act`, after the token preflight, because the candidate set depends on the pending-invitation list (Administration) |
| every live-vocabulary line (`invite`, `comment`, `supporters-append`, `revoke`, `cancel-invite` — including the sweep's `expired` re-arm lines, precondition (e) recovered `comment` lines, and the catch-up's `invite` `ok-catchup` / `supporters-append` lines (§11 step 4b)) | `act` | **after** the corresponding API call returned (never before; §5.2); ledger-only lines at the point the decision is made. - In `record-only`, the `act` job is **skipped by its `if:`**; the run log therefore shows `act` as skipped for every record-only run. That log line, the ledger check, and the GitHub-side audit (§5.3) together are the proof required by EPIC #119 Done-when.
- `decide` never issues a **write** (`PUT`, `POST`, `PATCH`, `DELETE`) to any endpoint under `/collaborators`, `/invitations`, `/comments`, `/contents/SUPPORTERS.md`, nor the GraphQL mutation `addDiscussionComment`. Reads (`GET`, GraphQL queries) of those resources are allowed in `decide` (the marker search and the audit need them). Child #2's CI MUST enforce this statically: a script that scans the **whole** `decide` job (every `run:`, `env:`, `with:`, and `if:` block, not only `run:`) and fails if (a) the string `SUPPORTER_LOOP_TOKEN`, any `TELEGRAM_*` secret, or the host `api.telegram.org` appears, (a′) a Contents `PUT`/`DELETE` targets a path other than the `ledger/` prefix (paths assembled from `env:` count — the scanner resolves job-level literals), or (b) a `gh api`/`curl` invocation with a write method targets one of those paths — write method = `--method PUT|POST|PATCH|DELETE`, `-X PUT|POST|PATCH|DELETE`, a GraphQL `mutation` string, **or, for `gh api`, any `-f`/`-F`/`--input`/`--raw-field` without an explicit `--method GET`, and, for `curl`, any `-d`/`--data`/`--data-raw`/`--data-binary`/`--json`/`-T` without an explicit `-X GET`** (those forms imply POST/PUT); `gh api graphql -f query='query…'` is a read and is allowed — or (c) `addDiscussionComment` appears (fixture-tested: one clean workflow, one violating per rule).
- Neither PAT may be exported as a job-level or workflow-level `env:`. Each is passed to exactly the steps that call the reward repo, as a step-level `env:`.
- No `actions/checkout`, no third-party actions, in any job. Only `gh`, `jq`, `curl`, `git` preinstalled on `ubuntu-latest`.
- `timeout-minutes` MUST be set on every job (≤ 10; `alert` ≤ 2).
- Run serialization per source repo is the caller's `concurrency` block (§4.3, single copy): one lane for tier events, one for sweeps (v2.0). The sweep ∥ event race is analysed in §4.3 and tolerated by construction; the central workflow MUST NOT assume it runs alone. Cross-repo ledger races are handled by §6.4; a **second source repo is a contract bump** that must define cross-repo delivery serialization (§7) before it is added.

## 5. Modes [frozen]

### 5.1 `record-only`

The workflow performs the full decision (§2, §3, §7) and writes one ledger line per **would-be action** (§6.2 cardinality) with the **would-** vocabulary. It MUST NOT: create an invitation, post a comment, edit `SUPPORTERS.md`, remove a collaborator, cancel an invitation, or send Telegram. It MAY: read the reward repo (collaborators; the `/invitations` probe is issued only to observe the required 403, §8.4 — the ledger token cannot list invitations) and the source repo (stargazers, comments), resolve a stargazer id to a login with `GET /user/{id}` (`GITHUB_TOKEN`, read-shaped — the record-only catch-up rehearsal, §11 step 4b), and append to the ledger. The only network writes in `record-only` are Contents API appends to the ledger in the family's own private repo with a Contents-only token (§4.4, §8); nothing reaches any person. Failures surface as red runs (GitHub notifies the owner of failed runs natively).

### 5.2 `live`

Same decision; the `act` job executes the actions and each executed action is ledgered with the **live** vocabulary *after* the API call returned (never before).

### 5.3 Action vocabulary and the machine check [frozen]

| `mode` | Allowed `action` values |
|---|---|
| `record-only` | `would-invite`, `would-comment`, `would-supporters-append`, `would-revoke`, `would-cancel-invite`, `skip` |
| `live` | `invite`, `comment`, `supporters-append`, `revoke`, `cancel-invite`, `skip` |

**Zero-external-send proof** for a record-only period is the following check over the ledger returning **0** lines, plus the Actions run list showing `act` skipped for every run in the period:

```sh
# 0 == proof. Any hit == contract violation (stop, checkpoint #7).
jq -c 'select(.mode=="record-only" and (.action|IN("invite","comment","supporters-append","revoke","cancel-invite")))' ledger/*.ndjson | wc -l
```

and, symmetrically, `mode=="live"` lines MUST NOT carry a `would-*` action. Child #2 MUST ship this check as a script in `caty-ai/.github` and run it in its own CI against fixture ledgers (one clean, one violating, expected 0 and non-0).

The ledger check proves the ledger is honest and `act` was idle; it does not by itself prove GitHub's state. The proof therefore has a **third, GitHub-side clause**, produced by the same script **at checkpoint #4** (the full zero-send form below, run by the owner or by a one-off sweep with both tokens, at the end of the record-only period). After the switch to live the *zero-send* form no longer applies (live rewards legitimately change the sets); live sweeps instead run — **inside `act`, after the token preflight** (it needs the pending-invitation list, §4.4 sweep job assignment) — a **reconciliation audit** with this exact model (GitHub changes state without a ledger event when a supporter *accepts*, and comments outlive generations, so the prediction is set-based, not line-based): (i) **access**: for every `actor_id` whose current generation is open and whose latest `invite` has a success result and is not re-armed by a later `expired` line, the actor MUST be in `collaborators ∪ pending-invitations` (either set — acceptance moves them between the two without a ledger line); (ii) **no strangers**: every collaborator or pending invitee of the reward repo MUST be either predicted by (i), present in the checkpoint-#4 baseline, or listed in `ledger/manual-allowlist.json` (owner-maintained, for hand-added collaborators); (iii) **markers**, two directions with different strength: (A, the fraud direction) every marker comment found on the source repo MUST correspond to some `comment` line with a success result **ever** written for that (`actor_id`, tier) — closures do not delete comments, so closed generations still count; (B) every such line whose `subject` thread **still exists and is readable** MUST still carry its marker — a deleted Issue/Discussion/PR or a moderated (deleted) comment self-exempts, because the append-only ledger cannot express "marker vanished" and deleting spam threads is normal hygiene; residual B-divergences the owner accepts are listed in `ledger/manual-markers-allowlist.json` (mirror of (ii)); any difference is reported (`::error::` **and a non-zero exit** of the sweep, so `alert` fires and Telegram is sent) and blocks destructive sweep steps (§11 precondition (d)), but is a reconciliation task, not a checkpoint-#7 stop. The audit's inputs are GitHub state and the **ledger only**: `SUPPORTERS.md` and `ledger/<name>.sweep-state.json` are derived files (§0-5, §6.5, §6.6) and are neither predicted-state sources nor audited sets — a stale or missing derived file is repaired by regeneration (§11 steps 6 and 8), never reported as a divergence. In `record-only` sweeps only the reduced form runs: the collaborator set equals the baseline (readable with the ledger token), the `/invitations` probe returns 403 (§8.4 — evidence that no credential able to invite was present), and the source-repo marker search (GraphQL/REST reads, allowed in `decide`, §4.4) returns 0; the pending-invitation comparison is deferred to checkpoint #4 because no token able to read it exists before then. A reduced-form pass is not a spurious violation; only a failed clause is.

**Zero-send form (record-only period only — checkpoint #4 / reduced form in record-only sweeps; the "checkpoint #7" consequence below belongs to this form alone, never to the live reconciliation audit):**

1. **Baseline**: at the moment the caller first runs in `record-only` (child #3's PR), the owner records `GET /repos/{reward_repo}/collaborators` and `GET /repos/{reward_repo}/invitations` (logins + ids) as `ledger/baseline-<YYYY-MM-DD>.json` in the reward repo.
2. **Audit**: the collaborator and pending-invitation sets of the reward repo equal the baseline (no additions), **and** a search of the source repo for comments containing the marker prefix `<!-- supporter-loop:` (Issues/PRs via REST, paginated to the end; Discussions via GraphQL) returns 0 for the period.

All three clauses = proof. Any one failing = contract violation → stop at checkpoint #7.

### 5.4 Switching

`record-only → live` = human checkpoint #4 (EPIC #119). Preconditions the requester MUST show: the §5.3 check = 0 over the whole record-only period; the full ledger; the exact comment text (§10); the list of logins that would be invited. The switch is the one-line change in §4.3 merged via PR to the source repo's default branch. `live → record-only` (rollback) is the same one-line change and needs no checkpoint.

## 6. NDJSON ledger [frozen] (`schema: 1`)

### 6.1 Location

- Repo: the **reward repo** (`inputs.reward_repo`, v1 `caty-ai/ask-ai-widget`), default branch.
- Path: `ledger/<source_owner>--<source_repo>.ndjson` (v1: `ledger/caty-ai--x-collector.ndjson`). One file per source repo.
- Written only via the GitHub Contents API (`PUT /repos/{reward_repo}/contents/{path}` with `sha` of the previous blob) using `SUPPORTER_LEDGER_TOKEN`; commit message `supporter-loop: <event> <actor> <action>`; committer identity `supporter-loop[bot] <supporter-loop@caty-ai.noreply>` (a label; not an account).
- The ledger lives in a private repo. It is **not** published; derived artifacts (`SUPPORTERS.md`) are.

### 6.2 Line schema

**Cardinality: one line per action attempt** (not per event). A first-contact tier-2 event produces up to three lines (`invite`, `comment`, `supporters-append`) plus, in the same run, any `skip` lines; all lines of one event share `run_id`. ISSUE-120's Done-when originally said "1事象1行"; it was amended on 2026-09-06 to "1 action attempt = 1 行" with a superseding-record comment (https://github.com/caty-ai/x-collector/issues/120#issuecomment-5553721814), so the Issue and this section agree.

One JSON object per line, keys in this order, no other keys in v1:

| Key | Type | Value |
|---|---|---|
| `schema` | int | `1` |
| `ts` | string | RFC 3339 UTC, second precision, from the runner clock |
| `run_id` | string | `${{ github.run_id }}-${{ github.run_attempt }}` |
| `repo` | string | source repo `owner/name` |
| `event` | string | `watch` \| `issues` \| `discussion` \| `pull_request_target` \| `sweep` |
| `actor` | string | GitHub login (never display name, never e-mail) |
| `actor_id` | int | GitHub numeric user id (stable across renames) |
| `tier` | int | `1` \| `2` \| `3` \| `0` (sweep closure / skip lines, excluded) — **v2.0**: a sweep *delivery* line (`event: sweep`, action `invite` / `supporters-append` from catch-up, or their `would-*` forms) carries `tier: 1`, because it delivers the tier-1 bundle and its `dedup_key` is the tier key (§7) |
| `subject` | string | `""` for `watch`/`sweep`; otherwise the HTML URL of the Issue / Discussion / PR |
| `action` | string | §5.3 vocabulary |
| `mode` | string | `record-only` \| `live` |
| `result` | string | `ok` \| `ok-backfill` (historical, v1 backfill — no longer produced) \| `ok-catchup` (v2.0 — an `invite` issued by the sweep's catch-up, §11 step 4b) \| `already-<tier>` \| `noop` \| `expired` \| `deferred-quota` (v2.0 — refused by the platform's rolling 24 h invitation limit, or declined as its sibling; on a `skip` line, the sweep's catch-up stop — §14) \| `excluded-<reason>` (§3.2 reason codes, plus the sweep-only `excluded-unresponsive`, §7) \| `tier-disabled` \| `error-<http-status\|code>` — success results are `ok`, `ok-*`, `already-*`, `noop`, `expired` (§7); `deferred-quota` is **not** a success |
| `dedup_key` | string | §7 |
| `gen` | int | generation counter for this `dedup_key` (§7), starts at `1` |

Forbidden content: Issue/PR/Discussion titles or bodies, e-mail addresses, display names, any token, any URL other than `subject`. Child #2 MUST build every line with `jq -n --arg …` from an allowlist of fields; free text from the event payload never reaches the ledger.

### 6.3 Append-only

Lines are only ever appended. Corrections are new lines (e.g. a later `revoke`). Rewriting history of the ledger file is a contract violation. The Contents API refuses writes to files larger than 1 MB, so the sweep MUST rotate the file when it exceeds **900 KB**: rename to `ledger/<name>.<YYYY-MM-DD>.ndjson` (a `PUT` of the new name, then — **only after re-reading the new blob and verifying it is byte-identical to the old** — a `DELETE` of the old, both via the Contents API; the *only* permitted deletion in this system, and the content is preserved under the new name. A crash between the two leaves base + copy while event runs keep appending to the base; the next sweep detects a rotated file whose content is a prefix of the base and **first re-`PUT`s the copy with the base's current content** (so lines appended after the crash are carried over), then `DELETE`s the base only when the two are byte-identical; base and copy may coexist during rotation or after a crash, but the base is always deleted rather than merged, and §7 counts closures per `run_id` and delivery by existence, so a transiently duplicated line can neither inflate a closure count nor change a delivery decision, and no appended line is lost) and start a new file; readers MUST glob `ledger/<name>*.ndjson` and concatenate in file-name order. If an append fails with the size error before rotation happened, the run fails loud (§14) and the next sweep rotates.

### 6.4 Concurrency

Appends use the Contents API compare-and-swap (`sha`). On `409` / `422 sha mismatch` the writer MUST re-read and retry up to 5 times with jitter; after that the job fails loud (`::error::`); in `live` the `alert` job (§4.4) sends the owner a Telegram failure notice, in `record-only` the red run itself is the signal (GitHub's native failure notification). A lost append is a *failed run*, never a silent drop.

### 6.5 `SUPPORTERS.md` (derived; format owned by child #1)

`SUPPORTERS.md` in the reward repo is regenerated (whole file) from the ledger by the `act` job after every live `invite` / tier upgrade / `revoke`, **and unconditionally on every live sweep** (v2.0 — step 6 of §11, also in red-run sweeps as §14 already promised; one GET + PUT per sweep; this closes the crash-between-append-and-regenerate corner and the sweep ∥ event race without any interleaving analysis). Contract-level rules only: one line per `actor_id` (a renamed account stays one line); content = the most recently ledgered login for that id (as `@login`), the **achieved tier** (§7 — success results only; `skip`/`error-*`/`deferred-quota`/`tier-disabled` lines never raise it), first-seen date; sorted by first-seen date; ids whose current generation is closed (§7) are omitted, **and so are ids whose achieved tier is exactly 1 and whose current-generation `invite` is not delivered under §7 (v2.0 — including an `expired` re-arm with no later successful `invite`, and an `excluded-unresponsive` stop): a tier-1 row shows only people who hold or have been offered access; a tier-2/3 row stays with its tier (§2.2 — recognition never decreases) and merely lacks the access until re-invited; after a successful re-invite the next regeneration restores a dropped tier-1 entry without another action line**; family/bot logins never appear; regeneration is a normal commit on the default branch. The header text, badge markup, and translations are child #1's.

**Regeneration order (v2.0, normative):** `GET` the current file `sha` → read the ledger (§6.3 glob) → render → `PUT` with that `sha`; on a CAS conflict (`409` / `422 sha mismatch`) restart **from the `GET`** (never re-fetch only the `sha` around a stale render), within the §6.4 retry budget. Because an event run ledgers `invite ok` *before* its own regeneration, any projection written before the sweep's `GET` is already in the ledger the sweep reads, and any written after it conflicts and is re-rendered.

Ledger semantics of regeneration: a regeneration caused by a tier event emits exactly **one** `supporters-append` (or `would-supporters-append`) line for that actor and `dedup_key`; a regeneration caused by the sweep's catch-up (§11 step 4b) emits exactly **one** `supporters-append` line **per actor for whom the sweep queued one** (§11 step 4b, "Step 6 closes the queue" — a re-invited actor whose `supporters-append` is already delivered gets no new line) (`event: sweep`, `tier: 1`, tier key — §7), all covered by the single end-of-sweep regeneration; a regeneration caused by `revoke` / `cancel-invite`, or the unconditional per-sweep regeneration with nothing delivered, emits **no** `supporters-append` line (the revoke line, or nothing, is the record).

### 6.6 `ledger/<name>.sweep-state.json` (derived latch, v2.0; owned by child B)

A second derived file lives next to the ledger: `ledger/<source_owner>--<source_repo>.sweep-state.json` (v2: `ledger/caty-ai--x-collector.sweep-state.json`). It is **not a ledger line** and is **not a ledger file** (readers glob `ledger/<name>*.ndjson` — §6.3 — so the `.json` suffix keeps it out of every ledger read); the action vocabulary (§5.3) and the line schema (§6.2) are untouched by it.

- Written by `act` at the end of every live sweep (§11 step 8) with `SUPPORTER_LEDGER_TOKEN` under the `ledger/` prefix — the `decide` scanner rule (a′) of §4.4 is unchanged and `decide` never writes it. Written in the same GET sha → render → PUT order as `SUPPORTERS.md` (§6.5).
- Content = counts and timestamps only: `last_sweep_ts`, `backlog` (candidates left unserved by catch-up), `cancelled_runs` (Actions-API count of `status=cancelled` supporter-loop runs since the §11(a) watermark, event vs schedule split — listed by `decide`, which holds `actions: read`, and handed to `act` as job outputs), `capacity_pct` (per §16 ceiling), `alarm_state` (which §16 alarms are currently raised). No login, no id, no token, no free text.
- Purpose = **owner-notification latch** for the edge-triggered alarms of §9 and a home for Actions-API facts that are not decisions. Nothing supporter-facing reads it (§0-5); the reconciliation audit ignores it (§5.3). If it is missing or unparsable, the sweep treats every alarm as *not previously raised* (so at most one duplicate Telegram is sent) and rewrites it.
- Like the ledger it is readable by invited supporters (they hold `pull` on the reward repo); it contains counts only, so that exposure adds nothing to §13.7.

## 7. Deduplication and idempotency [frozen]

- `dedup_key` = `"<repo>:<tier>:<actor_id>"` for **delivery** lines of a tier (e.g. `caty-ai/x-collector:1:184229851`) — on tier events **and, since v2.0, on the sweep's catch-up delivery lines** (`invite` / `supporters-append` and their `would-*` forms with `event: sweep`, `tier: 1`); `"<repo>:sweep:<actor_id>"` for sweep **closure and skip** lines (`revoke`, `cancel-invite`, their `would-*` forms, and every sweep `skip` — `excluded-*`, `excluded-unresponsive`, `deferred-quota`). **Key rule (v2.0):** the key follows the *action's meaning*, not the run that wrote it — a delivered tier-1 action has one key whichever path delivered it, so the per-action delivery test below needs no knowledge of the sweep.
- **Success results** = `result` equal to `ok`, starting with `ok-`, starting with `already-`, or equal to `noop` / `expired`. Everything else (`error-*`, `deferred-quota`, `excluded-*`, `tier-disabled`) is a non-success and never counts as delivered, achieved, or closing.
- **Achieved tier** of an actor on a repo (used by §6.5 and §11): the highest `tier` among lines with `.action` in {`invite`, `comment`, `supporters-append`} (live) or their `would-*` forms (record-only) **and a success result**, within the current generation. `skip`, `error-*`, `deferred-quota`, `tier-disabled` and excluded lines never raise it.
- **Generation** (per actor per source repo, shared by tiers 1–3): `gen(repo, actor_id)` = 1 + the number of **closure events**, where a closure event is one run (`run_id`) that wrote at least one line with `.repo == repo`, `.actor_id == actor_id`, `.action` in {`revoke`, `would-revoke`, `cancel-invite`, `would-cancel-invite`} **and a success result other than `expired`** — regardless of those lines' `dedup_key`. A `revoke` + `cancel-invite` pair from one sweep counts once; a failed revoke (`error-*`) closes nothing and is retried by the next sweep. A `cancel-invite` with `result: expired` (§11 step 2) is **not** a closure: it only **re-arms the `invite` action** — the actor's `invite` for the current generation is treated as not delivered from that line on, while `comment` / `supporters-append` stay delivered, so the next tier event of any tier re-issues the invitation and nothing else. The actor's next tier event of any tier after a closure opens the next generation and is rewarded again (tiers 1..N at once, §2).
- **Delivered, per action**: an action `X` ∈ {`invite`, `comment`, `supporters-append`} of tier N is delivered for (`dedup_key`, current `gen`) iff an earlier line exists with that `dedup_key`, that `gen`, `.action == X` (live lines) and a success result, **unless** `X` is `invite` and a later same-generation `cancel-invite` line with `result: expired` exists (re-arm, §11 step 2) with no successful `invite` after it. Sibling actions never block each other: a run whose `comment` succeeded but whose `supporters-append` failed retries only `supporters-append` at the actor's next event of that tier. In `record-only` the same rule applies to `would-X` lines among themselves (so the rehearsal ledger is also idempotent).
- **Rehearsal lines never satisfy live delivery.** A `would-X` line does not count as `X` delivered once the caller is `live`; the supporter's next qualifying event is delivered for real. Tier 1 has no natural re-trigger (one cannot re-star without unstarring), so a stargazer whose tier-1 bundle is undelivered — whether because the caller was `record-only`, because the event run was cancelled in a burst, because the invitation was `deferred-quota`, or because a sibling action crashed — is served by the sweep's **standing catch-up** (§11 step 4b, v2.0): in an open generation, "actor is a stargazer and a tier-1 action is not delivered" is simply an undelivered action, and the sweep delivers it. This supersedes the v1 one-off `backfill` (retired below).
- **Transition table** (the normative summary of this section; prose must agree with it). "Line" = the most relevant earlier line for (`dedup_key`, current `gen`, action `X`):

  | Existing line for (`dedup_key`, `gen`, `X`) | Next qualifying event | Result for `X` |
  |---|---|---|
  | none | any (either mode) | deliver (`X` or `would-X`) |
  | `X` with success result | live | `skip`, `result: already-<tier>` |
  | `X` with `error-*` only | live | deliver again (retry) |
  | `would-X` only | live | **deliver** (rehearsal does not count) |
  | `would-X` only | record-only | `skip`, `result: already-<tier>` |
  | `X` with `deferred-quota` only (v2.0) | live tier event; for tier-1 `X` also the live sweep catch-up | deliver again (`deferred-quota` is a non-success; the tier-1 bundle is re-attempted as a whole, §2; a deferred `comment` waits for the next qualifying event — catch-up never posts comments) |
  | tier-1 `X` not delivered (none / `would-X` only / `error-*` / `deferred-quota` / re-armed) in the current (open) generation, actor still a stargazer, no `skip` `excluded-*` line for the id in this generation | live sweep catch-up (§11 step 4b) | `invite`, `result: ok-catchup` (only if `invite` itself is undelivered) and/or `supporters-append`, `result: ok` — each **per action**, `event: sweep`, `tier: 1`, tier key; a delivered `invite` is never repeated, a stranded `supporters-append` is repaired alone |
  | `invite` with success result, followed by `cancel-invite` `result: expired` (§11 step 2) | any tier event **or** sweep catch-up | `invite` delivered again (re-armed); `comment` / `supporters-append` unaffected; same generation |
  | second `expired` re-arm in the same generation (two `ok*` invitations from either path, each followed by `expired`: `ok*` → `expired` → `ok*` → `expired`) — v2.0 **two-invitation bound on automatic catch-up** | sweep catch-up | one `skip`, `result: excluded-unresponsive` (`<repo>:sweep:<actor_id>`, written by `act`); the id leaves the catch-up candidate set for this generation. The bound limits catch-up only: the person's own next tier event still delivers normally and may issue a further invitation (§3 exclusions are payload-derived, and `excluded-unresponsive` is a sweep-only skip, not an eligibility rule); a new generation resets the bound |
  | generation closed (closure event) | any tier event (1, 2 or 3 — a tier-2/3 event after closure delivers tiers 1..N at the new generation) | new generation; all actions deliverable again |
- **Backfill (retired in v2.0).** v1 defined a one-off, owner-authorized `backfill` sweep input (checkpoint #4) that turned `would-invite` lines into `invite` `ok-backfill`. The standing catch-up of §11 step 4b absorbs it: a `would-invite` in an open generation with the actor still a stargazer is an undelivered tier-1 action like any other. Child B removes the input (removing an input is a bump — this is that bump, §1); `ok-backfill` remains a recognised **historical** success result so v1 ledger lines keep their meaning. Tier-2/3 `would-comment` / `would-supporters-append` lines are still never backfilled — the moment has passed; the supporter's next Issue/PR is delivered by the "rehearsal does not count" row.
- **Catch-up candidate set (v2.0, precise).** For the live sweep, the candidate set = every numeric id in the exhaustive stargazer list (§11(b)) whose current generation is open, for which at least one tier-1 action (`invite`, `supporters-append`) is **not delivered** per the rule above (the `expired` re-arm un-delivers `invite`), and for which **no** `skip` line with `result` starting `excluded-` exists for that `actor_id` in the current generation, **regardless of `dedup_key`** (event-path skips at any tier key — including an `excluded-member` written on a tier-2/3 event, the only place membership is visible — and sweep skips at `<repo>:sweep:<id>` all count; a `deferred-quota` skip does **not** — it is a prefix filter, so the stop line of one sweep never self-excludes the refused candidate). The candidate set is **empty unless tier 1 is in `inputs.tiers_enabled`** (§4.2): a `skip` / `tier-disabled` line is not an exclusion, but a disabled tier suppresses catch-up delivery of that tier entirely. Ordering = two groups — **never-invited** candidates, then **re-armed** ones — each preserving the stargazer listing's **page order** (oldest Star first). Dedup MUST keep the **first occurrence** of each numeric id in the concatenated page sequence with a stable operation (e.g. a jq `reduce` over a seen-id set); jq `unique` / `unique_by` MUST NOT be applied to the ids (both sort by key — measured: `[9,2,9,5] | unique_by(.)` → `[2,5,9]`, the required result is `[9,2,5]`), and nothing sorts by actor id. Fixture (child B): pages flattening to `[9,2,9,5]` yield `[9,2,5]` before the never-invited / re-armed partition. A historical `ok-backfill` `invite` line (v1) counts as a delivered `invite` for candidate selection under either key, and B counts it (§11 step 4b). Stated assumption: the page order of `GET /repos/{source_repo}/stargazers` is `starred_at` ascending; the contract relies on that order, MUST NOT sort, and MUST NOT request the `star+json` media type (the `stars` job output stays ids-only, §4.4). Identity (`GET /user/{id}`, `GITHUB_TOKEN`) and the §3 filter are applied only to the candidates actually taken (§11 step 4b), so identity calls per sweep ≤ Q + excluded found, where Q is the invitation quota of §16.
- Comment idempotency is additionally guarded on the GitHub side: before posting, `act` MUST search the target thread for a comment **authored by the workflow identity (`github-actions[bot]`)** containing the marker `<!-- supporter-loop:tier<N>:<actor_id> -->` — Issues/PRs via `GET /repos/{source}/issues/{n}/comments` **paginated to exhaustion** (`Link` header), Discussions via GraphQL `repository.discussion.comments` **and their `replies`** paginated to exhaustion (`pageInfo.hasNextPage`); the Issues comments API MUST NOT be used for `event=discussion`. Any fetch/parse error or truncation MUST abort **before** posting (fail closed). If the marker is found, ledger `action: comment`, `result: already-<tier>` (a success result → delivered) without posting. This covers a ledger append that failed after a comment was posted.
- Invitation idempotency is **not** assumed from the API. Before every `PUT /repos/{reward_repo}/collaborators/{login}`, `act` MUST (a) check `GET /repos/{reward_repo}/collaborators/{login}` (204 = already a collaborator → ledger `invite`, `result: already-1`, no PUT) and (b) list `GET /repos/{reward_repo}/invitations` to exhaustion and match `invitee.id == actor_id` (match → ledger `invite`, `result: already-1`, no PUT). Only then PUT with `{"permission":"pull"}`; 201 and 204 are `ok`. GitHub invitations **expire after 7 days**; the event path never inspects the 7-day clock itself — the sweep (§11 step 2) writes the `expired` re-arm line first, and only then does the actor's next event re-issue the invitation (§7 delivered-per-action rule).
- Same-run re-delivery: a re-run of a workflow (`run_attempt > 1`) re-evaluates against the ledger like any other run; because live lines are written only after the API returned (§4.4), a crash between the API call and the append is recovered by the GitHub-side checks above (marker search; collaborator/invitation preflight).

### 8.1 The credentials (two, single-purpose)

| | `SUPPORTER_LEDGER_TOKEN` | `SUPPORTER_LOOP_TOKEN` |
|---|---|---|
| Purpose | ledger read/append, `SUPPORTERS.md` regeneration, `ledger/<name>.sweep-state.json` regeneration (§6.6, v2.0), ledger rotation | collaborator invitations, revokes, invitation cancellation |
| Used by | `decide` (both modes) and `act` | `act` **only** (never present in `record-only` runs) |

| Resource owner | `caty-ai` | `caty-ai` |
| Repository access | **Only selected repositories: `caty-ai/ask-ai-widget`.** Nothing else. Adding a repo is a §8 bump + checkpoint #2 again. | same |
| Repository permissions | **Contents: Read and write** · **Metadata: Read** (implied) — nothing else | **Administration: Read and write** (`PUT/DELETE /repos/{r}/collaborators/{login}`, `GET/DELETE /repos/{r}/invitations`) · **Metadata: Read** (implied) — **no Contents write** |
| Organization / account permissions | none | none |
| Expiry | ≤ 366 days; dates recorded at checkpoint #2 as caller-repo *variables* (not secrets) `SUPPORTER_LEDGER_TOKEN_EXPIRES` / `SUPPORTER_LOOP_TOKEN_EXPIRES` = `YYYY-MM-DD`; the sweep warns (`::warning::` and, in live, Telegram) 14 days before either date. | same |
| When registered | checkpoint #2 (needed for the first record-only run) | may be issued at checkpoint #2 and registered then, or deferred to checkpoint #4. **Preflight**: the first step of `act` checks that the token is non-empty and passes §8.4's loop-token self-check; every other step of `act` (comments, `SUPPORTERS.md`, ledger, Telegram) depends on that step, so an empty or wrong token produces zero sends and a red run, never a partial delivery |

### 8.2 Where they are stored

Reusable workflows receive secrets only from their caller. Both tokens are therefore an **Actions secret of the caller repo `caty-ai/x-collector`** (Settings → Secrets and variables → Actions), exactly like `TELEGRAM_BOT_TOKEN` there today. It is *not* stored on `caty-ai/.github` (a secret there would be invisible to the caller). If a second source repo is added later, the secret is registered on that repo too, or promoted to an org secret restricted to the source repos — either way the permission set in §8.1 is unchanged.

> Note for EPIC #119 Done-when: the line "招待トークンは `caty-ai/.github` の Actions secret にのみ存在し" is not technically achievable for a reusable workflow. This contract fixes the storage as the caller repo's Actions secret; the EPIC wording is to be amended by the owner at checkpoint #2 (contract-level wording change → recorded, not silently edited).

### 8.3 What the tokens are never used for

- Never called against the source repo (`caty-ai/x-collector`) — comments, labels, and reads there use `GITHUB_TOKEN` — except the two read-shaped §8.4 over-scope probes (`GET /repos/{source_repo}/invitations`, which MUST fail), whose only purpose is to prove that this rule holds. (v1.11 wording; the stargazer listing needs `contents: write` on a `GITHUB_TOKEN` and is not a PAT read — §4.4 `stars`.)
- `SUPPORTER_LOOP_TOKEN` is never referenced in the `decide` job (§4.4 static check) and therefore never materializes in a `record-only` run.
- Never passed to Telegram, never written to the ledger, never printed. GitHub masks it in logs automatically; child #2 MUST additionally ensure no step echoes request bodies or headers (`curl -sS` without `-v`, `gh api` without `--verbose`).
- `SUPPORTER_LEDGER_TOKEN` is present in `decide` only for the ledger operations (read, append) and the §8.4 self-check and over-scope probes, each with step-level `env:`; it cannot invite (no Administration permission) even if misused.

### 8.4 Positive self-check (child #2, run at every `sweep`)

Ledger token: `GET /repos/{reward_repo}` (200) · `GET /repos/{reward_repo}/contents/ledger` (200) · `GET /repos/{reward_repo}/collaborators?per_page=1` (200 — the reduced-form audit, §5.3, depends on this read; if the platform ever denies it to a Contents-only token, the sweep goes red visibly and §5.3's reduced form is amended, not silently skipped) · `GET /repos/{reward_repo}/invitations` MUST be 403 (proves it has **no** Administration). Loop token (live runs only, inside `act`): `GET /repos/{reward_repo}/invitations` (200 — the endpoint that actually requires Administration read) · `GET /repos/{reward_repo}/contents/ledger` MUST be 403/404 (proves no Contents access). Over-scope probe for both tokens (read-shaped, so the probe itself can never change anything): `GET /repos/{source_repo}/invitations` (needs Administration on the source repo) MUST return 403/404, and `GET /repos/{reward_repo}` with the loop token MUST return 200 (reachability only — its `permissions` object reflects the **token owner's repository role**, not the fine-grained grant, so an org-owner-issued token always shows `push: true`; the loop token's Contents 403/404 probe above is the push-impossibility proof — v1.10; a non-200 here is a reachability failure, reported as `::error:: reward repo preflight failed`); any unexpected success of a 403/404 probe is reported as `::error:: token over-scoped` (and, in live, Telegram'd) and the sweep performs no destructive action in that run. A fine-grained PAT restricted to selected repositories has **no** access to other repositories, public or not (v1.11 correction, measured: `GET /repos/{source_repo}/stargazers` with the ledger token → 403 "Resource not accessible by personal access token"); the probes above therefore prove scope, not merely least privilege on writes. As in the errmeter contract §8 (https://github.com/caty-ai/errmeter/blob/epic/1/docs/contract.md), a 403/404 is consistent with least privilege but not proof; the authoritative check is the owner looking at the token's permission page at checkpoint #2.

### 8.5 Residual blast radius (acknowledged)

`Administration: Read and write` is the platform minimum for collaborator and invitation management on a fine-grained PAT, and it also permits renaming, archiving, or deleting the reward repo. This is accepted for v1 because the repo is a low-stakes early-access shelf, the ledger and `SUPPORTERS.md` are small and reconstructible from GitHub's own stargazer/collaborator state, and no alternative permission exists. Mitigations the owner SHOULD apply at checkpoint #2: token expiry ≤ 366 days; the reward repo's default branch protected by a ruleset (the token's Contents write still passes through it for `ledger/` and `SUPPORTERS.md` because the ruleset targets force-push/deletion only); and a note in the token description naming this contract.

## 11. Sweep (twice daily) [frozen]

Triggered by the caller's `schedule` (§4.3 — twice daily, 12 h apart, v2.0) with `sweep: true`, or by a `workflow_dispatch` of the caller (write access to the caller repo required — v2.0 wording, #141; identical steps; the central workflow accepts exactly these two event names for a sweep and refuses `sweep: true` on any tier event before any network access). The sweep runs in its own concurrency lane (§4.3) and is therefore never cancelled by a tier event; it is the **reconciler** — event runs are the fast path, the sweep is the truth (§16). The step order below is normative (the audit must see the expiry re-arm before it judges, and the destructive step must see the audit). Job assignment is fixed by §4.4 ("Sweep job assignment"): `record-only` → all steps in `decide` (reduced); `live` → step 1 ledger half + preconditions (a)(b) and the step-8 run listing in `decide`, everything else in `act` after the token preflight.

**Fail-closed preconditions for any destructive step (step 4 only — unstar cleanup and the defensive API cancels queued by step 2).** Before revoking or cancelling anything via the API the sweep MUST establish, and fail loud + skip all destructive steps if any is false (ledger-only steps — the expiry re-arm and the audit itself — are never gated, because they are what makes the preconditions satisfiable): (a) `GET /repos/{source_repo}/actions/workflows/supporter-loop.yml/runs?status=failure&created=%3E%3D<T>` (the **per-workflow** listing — v1.11; the `>=` is URL-encoded) filtered to the supporter-loop workflow path returns **zero** runs, where `<T>` = `created_at` of the most recent *successful* sweep run — **`event=schedule` or `event=workflow_dispatch`, `status=success`** (v2.0, #141 item 2: a green live sweep proves that this precondition held when it ran, because a gated-off live sweep exits red; so a successful dispatch advances the watermark exactly like a scheduled one) — from the same per-workflow runs API, or, if none exists yet, the `created_at` of the caller workflow's first run (the query is never issued with an empty timestamp); the runs listing is **paged to exhaustion** and, if the API's 1 000-result cap or any page error is hit, the precondition is treated as **false** (fail closed, same rule as stargazers) (a red run may have delivered a reward whose ledger line is missing; a human reconciles it first). The repository-wide `GET /repos/{source_repo}/actions/runs` MUST NOT be used for this: it counts every workflow in the source repo and exceeded the cap (1 691 runs) before any sweep had ever succeeded, so the precondition could never become true (run 34100523613, v1.11). The caller file name `supporter-loop.yml` is part of this clause (it is the per-workflow path and the `.path` filter): renaming the caller is a contract bump. **Reconciling a red run** (v1.11): the listing itself is the watermark, so a red supporter-loop run keeps this precondition false until either a later scheduled sweep succeeds — impossible while the red run is counted — or the owner, having reconciled its ledger effect by hand, **deletes the run** (`DELETE /repos/{source_repo}/actions/runs/{id}`, an owner action recorded on the lane's Issue with the run id and what was reconciled); deletion is the acknowledgement, and the workflow never deletes runs itself. **Owner runbook (v2.0)**: reconcile-or-delete a red run **within 24 h** — while it stands, every sweep (now two a day) skips steps 4 and 4b and itself ends red (§14), so the invitation backlog grows by the day and each red sweep is one more run to delete; the §9 red-run transition message and the `alarm_state` latch (§6.6) make the condition legible as one alarm transition, while the per-run `alert` (§4.4) still fires on each red sweep — which is the reason for the 24 h runbook; (b) the stargazer list (`GET /repos/{source_repo}/stargazers`, paged by the sweep-only `stars` job with a `GITHUB_TOKEN` carrying `contents: write` — the only credential the platform accepts there: measured 2026-09-07, `contents: none`/`read` → 403 `X-Accepted-Github-Permissions: metadata=read; contents=write`, GraphQL → FORBIDDEN, unauthenticated → 401, the ledger PAT → 403 — v1.11) was paged to exhaustion and handed to `decide` intact (a skipped or failed `stars` job, or an output that is not an array of positive integers, makes this false); In order:

1. §8.4 self-check.
2. **Expired invitation re-arm** (ledger-only, ungated; any defensive API cancel it identifies is queued for step 4) (**live only**; this step is a no-op in `record-only` and MUST NOT emit `would-cancel-invite` for `would-invite` lines — nothing was invited, and touching those generations would hide the undelivered action from catch-up, §11 step 4b): GitHub repository invitations expire **7 days** after creation. 3. **Reconciliation audit** (§5.3 live form; in `record-only` the reduced form). Runs **after** step 2 so that invitations that just expired are already re-armed in the ledger and are not counted as "predicted present". A divergence here sets precondition (d) false for the rest of this sweep.

For each remaining candidate in order: re-evaluate B **before every `PUT`** from the in-memory ledger + pending list using timestamps (a single snapshot at sweep start phase-locks the batch to a 36 h cycle); **Q = max(0, 45 − B)** (event runs may have used the platform's full 50, so 45 − B can be negative; no pass-2 `PUT` happens until B < 45); if Q = 0 while candidates remain and the oldest counted invitation ages out within **≤ 5 min** *and* that wait fits the remaining **cumulative** per-sweep wait budget of **≤ 3 min** (dynamic, per candidate — never a static slice of Q), wait for that moment and re-evaluate; **otherwise pass 2 stops** for this sweep without a further `PUT` — no lines for the unserved candidates, `backlog=<n>` exactly as in the 422-stop case; then resolve the login (`GET /user/{id}`, `GITHUB_TOKEN`), apply the §3 rules exactly as the event path does — an excluded id is ledgered once, `skip` / `excluded-<reason>` (`<repo>:sweep:<id>`, written by `act`), and the next candidate refills the slot — then deliver the **undelivered** tier-1 actions only: `invite` (`result: ok-catchup`) via the §7 preflight and `PUT` with `{"permission":"pull"}`, ledgered after the `PUT` returned; the actor's `supporters-append` is **queued iff it is itself undelivered** (a re-armed actor whose `supporters-append` is still delivered gets no queue entry and no new line — the unconditional regeneration alone restores the row) and its line (`result: ok`) is written after step 6's successful regeneration — `event: sweep`, `tier: 1`, tier key, one line per action. **Step 6 closes the queue**: one render + `PUT` of `SUPPORTERS.md` for every queued actor (pass 1 and pass 2 together); the next live sweep's pass 1 repairs the projection). **Two-invitation bound (limits automatic catch-up only):** the sweep MUST NOT issue another invitation once two qualifying `ok*` `invite` records in this generation — counted from **both** paths, whichever wrote them, duplicates normalised — have each been followed by an `expired` re-arm;    - **Record-only parity.** The reduced sweep in `decide` runs the same candidate selection (ledger-only: the quota term "pending without a ledger line" needs Administration and is unavailable — a stated undercount, harmless because rehearsal never sends), the same identity read and §3 filter, and writes `would-invite` / `would-supporters-append` (tier key, `event: sweep`, `tier: 1`) or `skip` / `excluded-*` (its normal authorship, §4.4). Rehearsal neither reads nor writes `sweep-state.json`. Fixture (child B), two parts: (i) **parity** — on a ledger with **no prior delivery history of either vocabulary for the candidates** (no `would-*` lines and no live `invite` / `supporters-append` lines in their current generation — live-only partial history such as an `invite ok` without its append is by design a pass-1 repair in live and a full prediction in rehearsal, so it is excluded from the parity set), identical eligibility, gate and expiry states, an empty unledgered-pending set and no live-only expiry difference, rehearsal predictions ≡ live decisions after vocabulary normalisation (`would-X` ↔ `X`); (ii) **the intentional migration difference** — successful `would-*` history suppresses a repeated rehearsal (§7 "rehearsal lines are idempotent among themselves") but does **not** suppress live catch-up (§7 "rehearsal lines never satisfy live delivery"). ## 13. Security invariants (mirror in the workflow header, do not weaken) [frozen]

1. NEVER `actions/checkout` (or any code execution from the triggering ref) in the central workflow or the caller. `pull_request_target` runs with secrets and a write token; that is safe only because untrusted code is never checked out or executed.
2. Actor-controlled strings enter `run:` scripts only via `env:` or `$GITHUB_EVENT_PATH`.
3. Secrets are limited to the four declared in §4.2/§4.3; no `secrets: inherit`; each PAT at step-level `env:` only, and only in steps that call the reward repo (the §8.4 read-shaped over-scope probes against the source repo are the one exception, and they MUST fail). `SUPPORTER_LOOP_TOKEN` (Administration) is referenced **only in the `act` job** — enforced by child #2's static check (§4.4). No secret is referenced in the `stars` job (v1.11).
4. Both PATs go only to `api.github.com` for `{reward_repo}` (plus the §8.4 probes above); Telegram secrets go only to `api.telegram.org`. Secrets are never echoed, never ledgered, never in a Telegram body. `contents: write` on a `GITHUB_TOKEN` exists only in the sweep-only `stars` job (v1.11, §4.4) — `decide` and `act` are `contents: none` on every event.
5. `record-only` cannot send: (i) the only long-lived credential loaded in a record-only run cannot invite (Contents-only on the reward repo, §8.1) — the sweep-only `stars` job's `GITHUB_TOKEN` (v1.11) is ephemeral, scoped to the source repo, confined to one `GET` (§4.4) and cannot invite either; (ii) the `act` job is gated by `if: inputs.mode == 'live'` (§4.4); (iii) every outbound call in `act` is additionally guarded by an explicit `[ "$MODE" = live ]` test in the script; (iv) Telegram is live-only (§9). All four must fail together for a supporter-facing record-only send, and (i) makes an invitation impossible regardless of the other three.
6. No third-party actions.
7. Supporter-facing output is limited to: one collaborator invitation to `{reward_repo}`, one comment on the actor's own thread per tier, `SUPPORTERS.md`. Anything else (e-mail, DM, mentions of third parties, comments on other people's threads) is out of contract.
8. Comment bodies are fixed templates with two substitutions (§10).

| Content-write secondary limit (403 with the abuse/secondary-rate-limit message, or `Retry-After`) — v2.0 | the affected write is ledgered `error-403` (an `invite` `PUT` under the row above; a ledger append fails loud under §6.4 after its retries); the job ends red and `alert` fires. ## 16. Capacity — ceilings, alarms, budget, owner rules [frozen] (v2.0)

Every number below was measured or taken from GitHub's documentation on 2026-09-08 (design record `design-v1.3.md` §0/§1). Symbols: **S** stargazers · **N** open-generation tier-1 supporters · **E** tier events per day · **F** ledger files · **P** pending invitations · **C** comments in the source repo · **B** invitations consumed in the current 24 h window. All figures are **lower bounds without retries or pagination overhead**.

### 16.1 Design stance

Event runs are the **fast path**; the sweep is the **truth** (§11). Two platform facts made v1 lossy under a burst and are the reason for v2.0: (D1) a concurrency group with `cancel-in-progress: false` keeps one running + **one** pending run and cancels every other pending run — cancelled ≠ `failure`, so v1 lost ≈ 75 of 100 Stars in 10 minutes silently and let a Star cancel the pending sweep; (D2) repository invitations are capped at **50 per repo per rolling 24 h**, the 51st `PUT` returns 422. v2.0 answers D1 with the sweep lane (§4.3) and standing catch-up (§11 step 4b), and D2 with the quota queue (§11 step 4b, §14). Everything else in this section is a **ceiling with an alarm**, not a mechanism — mechanisms are built when an alarm fires (§16.4).

### 16.2 Ceilings and alarms (alarm at 70 % of the ceiling, edge-triggered, §9)

| # | Part | Cost / capacity | Ceiling | Alarm | Failure shape at the ceiling |
|---|---|---|---|---|---|
| 1 | `stars` job (full REST paging, one `GET` per 100) | ⌈S/100⌉ requests ≈ 0.6 s each; output ≈ 10 B × S, emitted twice (`stars` → `decide` → `act`) | **S = 40,000** (job-output guard 400,000 chars, self-imposed — until the encoded size at the boundary is measured, child E) · S ≈ 80,000 time-bound (`timeout-minutes: 10`) · S ≈ 100,000 `GITHUB_TOKEN` 1,000 req/h per repo shared by every workflow in the source repo | S ≥ 28,000 | fail-closed (`sweep_gate=false`, red sweep, Telegram) |
| 2 | Tier event runs under a burst (D1) | 1 running + 1 pending per lane | sustained arrival > ≈ 2.5 Stars/min loses event runs | `cancelled_runs` > 0 in a sweep window (reported, §6.6) | **no loss** in v2.0: the cancelled Star is caught by catch-up at the next sweep (≤ 12 h) |
| 3 | Invitations (D2) | 50 / repo / rolling 24 h | **45/day by catch-up** (sweep path); events may use the platform's full 50 | `backlog` > 0 (reported every sweep) | `deferred-quota`, loud and ledgered; never silent |
| 4 | Ledger read per run | 2 × (2 + F) `GET`s + `jq -s` over L lines; ≈ 2,600 lines per 900 kB file; tier-1 supporter ≈ 2 lines | F = 10 (≈ 25,000 lines, ≈ 10,000 supporters) — est. ≈ 24 `GET`s/run, **unmeasured** | F ≥ 3 archived files | latency, PAT budget |

| 6 | Marker reconciliation + audit (§11(e), §5.3) | ⌈C/100⌉ `GET`s + Discussion pages + one existence read per ledgered subject | grows with repo activity (C = 279 today → 3 pages) | — | sweep time |
| 7 | Ledger rotation | one rotation per UTC day (archive name `<name>.<YYYY-MM-DD>.ndjson`, §6.3) | a second rotation on one UTC day fails loud ("archive already exists") | — | red sweep; reachable sooner with a daily cadence — noted, not solved |

### 16.3 API budget

- **`GITHUB_TOKEN`**: 1,000 requests/h **per repository, shared by every workflow in the source repo** (15 today). Sweep: ⌈S/100⌉ + runs listings (3–4) + ⌈C/100⌉ + Discussion pages + `GET /user/{id}` ≤ Q + excluded candidates found (§7; typically ≤ 50, bounded in the worst case by the §11 step 4b work budget) + one per revoke. Tier-1 event: 1 read; tier 2/3 add the marker-search pages + 1 write.
- **PATs** (both are the owner's user, so the budget is shared with every other tool the owner runs): 5,000 requests/h primary; **500 content writes/h and 80/min secondary — these bind first**. Tier-1 live event ≈ 17 + 2F + ⌈P/100⌉ requests of which **4 are content writes** (invite, 2 ledger `PUT`s, `SUPPORTERS.md`) → **≈ 125 tier-1 events/h** at the secondary limit (≈ 20/min at the per-minute limit; ≈ 250/h at the primary limit, F = 1). Live sweep ≈ 20 + 3F requests baseline + 3 per revoke + ≈ 8 per catch-up (3 writes each); 45 catch-ups ≈ 382 requests, ≈ 137 writes, paced at ≤ 1 write/s (§4.4) ≈ 2.5 min.
- Worked rows (F = 1, P ≤ 100): N = 100 / 1,000 / 10,000 → sweep baseline ≈ 23 requests in each case, plus catch-ups. Launch burst of 300 Stars in 2 h → the event path delivers ≤ 50 the first day, catch-up the rest at 45/day (≈ 6 more days). Steady E = 10 / 50 / 200 per day → nothing hourly if spread; **125 tier-1 events in one hour** hits the secondary limit (→ `error-403`, red run, Telegram — never silent).

| Tier-2/3 late thanks via the sweep (Issues/PRs since `<T>` by non-excluded authors, marker search, late comment) | cancelled `issues` / `pull_request_target` runs > 0 in a sweep window |

### 16.5 Honest service bound and residuals

- Under a saturated backlog, catch-up delivers **45 invitations per rolling 24 h**. The batch slot can slip once by 12 h after positive cron jitter (worst gap ≈ 36 h; amortised rate unchanged). Invitations invisible to B can produce a green `deferred-quota` stop on up to two consecutive sweeps (≈ 24 h). Every case is loud (`backlog=<n>` in each sweep summary), and anyone with write access can `workflow_dispatch` a sweep as soon as the window has room.
- **Residual (documented, not solved)**: an invitation that is accepted **and** unledgered within 24 h is invisible to B — covered by the 45/50 margin, the owner rule below and gate (a); the failure is a loud 422 that stops one sweep's catch-up, never a silent loss.
- Sweep ∥ event revoke/re-invite race: bounded to ≤ 24 h loss of access, self-healing at the next sweep, ledgered (§4.3).

### 16.6 Owner rules during a launch window

Stated plainly, because the PATs share the owner's account-wide budget: during a launch window **do not** run bulk owner tooling on the same account (multi-repo scans, bulk `gh api`, automated pushes with the owner's PAT), **do not** invite anyone to the reward repo by hand, and **do not** edit `ledger/`, `SUPPORTERS.md` or `sweep-state.json` by hand (CAS windows). Reconcile-or-delete any red supporter-loop run within 24 h (§11(a)). The loop fails loud (`error-403`, red run, Telegram) — never silently.
